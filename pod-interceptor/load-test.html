How the test was runmethod, scoring and pass criteria

Why the load is applied this way

Load was applied as an : requests go out on a fixed schedule regardless of how quickly earlier ones come back. That is how a real cluster behaves — pods get created because workloads are being deployed, not because the interceptor is ready — and it is the only shape in which a queue building up becomes visible. A closed-loop test would quietly slow its own request rate to match the server and hide the problem.

Each rate step ran in its own process, so no step inherited the previous one’s warmed-up state: 60 seconds of measured load per step, preceded by a 5-second warm-up excluded from every number in this report.

What one request contains

Every request is a complete Kubernetes AdmissionReview for a two-container pod, identical in structure to what the API server sends. Each pod is owned by a Deployment through a ReplicaSet — the the interceptor has to resolve. Real ReplicaSets and Deployments were created in the cluster so that walk was genuine, not simulated.

The owning workload for each request was chosen uniformly at random from 3,000 distinct workloads. That is the pessimistic choice on purpose: it mostly misses the interceptor’s internal owner cache, so the measured cost is close to the cache-miss cost of every request. Production traffic, where pod creations cluster around a few workloads, hits that cache far more often.

How each request was scored

The test seeds the recommendation data itself, so it knows the correct outcome for every request before sending it. Each response falls into exactly one class:

Scope and limitationswhat this run does not establish

What this test does not establish, stated plainly so the results are not read wider than they support.

  • The ceiling was not found. The highest rate tested passed, so 100 req/s is a demonstrated floor on capacity, not a measured maximum.
  • This is not a soak test. The longest continuous period of load was 60 seconds. Slow effects — resource leaks, database growth over days, certificate rotation — are outside its reach. Memory and concurrency were flat within each window, which is evidence against accumulation but not a substitute for a long-duration run.
  • Log verbosity matters and was set to ERROR. The interceptor ships log lines synchronously, so per-admission log volume is a direct cost on the admission path. Internal testing at high verbosity, with every line shipped to a remote collector, reached its limit at an order of magnitude lower rate — while CPU and memory stayed low, which is why that failure mode is invisible to resource dashboards. These results apply to a interceptor running at ERROR or WARN level, the shipped default.
  • Single replica, single cluster, one run. No horizontal scaling, no cross-region latency, and no repetition for run-to-run variance. Absolute numbers will shift with node type, database placement and cluster load.
  • The API server was not in the path. Load was applied directly to the interceptor’s endpoint, so these numbers are the interceptor’s contribution to pod admission time, not end-to-end pod creation time.
  • The data set was pre-existing. Recommendation rows were seeded by an earlier identical run and re-verified before this one, so database writes during the run reflect updates rather than fresh inserts.
  • Measured on a pre-release development build. Results should be re-confirmed against the release build before being quoted as product characteristics.
Reproducing this runthe exact invocation

The harness runs as a Kubernetes Job inside the target cluster. It seeds its own data, verifies it survived a round trip before sending any load, drives the endpoint, scrapes the interceptor’s metrics during each scoring window, and emits the results file this report is generated from.

run-job.sh \
    --mode MIXED --chain-share 100 \
    --owners 3000 --containers 2 \
    --rates 10,20,30,50,100 \
    --duration 60 --warmup 5 \
    --patch-ratio 90,0,10 --owner-dist uniform

Teardown removes the Deployments and namespaces the harness created and marks its seeded rows stale. It does not delete them, so a cluster used repeatedly for this test accumulates test data; absolute numbers are best compared within a session rather than across sessions.

Glossarythe terms used in this report
TermMeaning
Mutating admission webhookAn HTTPS endpoint the Kubernetes API server calls while a resource is being created. The endpoint may return a patch, which the API server applies before the object is persisted and scheduled. The Sedai Pod Spec Interceptor is registered on pod creation, so it sees every pod the cluster creates and can apply the recommended configuration before the pod starts.
Mutation yieldOf the admissions that should have received a patch, the share that actually received it inside the webhook timeout. It is the headline metric because the webhook is registered with failurePolicy: Ignore: if the interceptor answers late, the API server admits the pod anyway, without the optimization and without raising any error. A slowdown therefore shows up as work quietly not being done, not as a failure — which is exactly what this number is built to catch.
p99 and other percentilesThe response time that 99% of requests came in under; 1 in 100 took longer. p50 is the typical response, p99.9 the slowest 1 in 1,000. Percentiles are used instead of averages because an average hides the tail, and the tail is what crosses a timeout.
Cores and millicoresKubernetes CPU units. 1,000 millicores (written 1000m) is one CPU core. The interceptor in this test was configured with a 500 m limit — half of one core — and an equal request, so that half core is also guaranteed to it.
Ownership chainThe path from a pod up to the workload that owns it: pod → ReplicaSet → Deployment. The interceptor has to walk it to find which recommendation applies to the pod it is being asked about. Every request in this test used that full chain, which is the most expensive case: two database lookups plus a live Kubernetes API call per request.
Open-loop loadRequests are sent on a fixed schedule regardless of how quickly earlier ones come back — the way a real cluster creates pods. The alternative, closed-loop load, waits for each response before sending the next, so it silently slows down when the server does and can hide a backlog completely. Open-loop is the only shape in which a queue becomes visible.
