How Sedai supports Expedia’s progressive deployment

Expedia rolls out changes with progressive deployment (PD): a blue and a green Deployment run side by side while traffic shifts from one to the other. Sedai handles this with two independent mechanisms. Blue/green topology handling merges the two colours into one stable logical app and pauses automated actions during a cutover. Annotation-driven settings let Expedia hold a workload in DATA_PILOT for as long as PD is live.

02Blue/green topology handling

On every topology refresh, Sedai turns each blue/green pair into one logical app with a stable ID. While both colours claim the same role, it also pauses every automated action on that app.

Which annotations Sedai reads

Sedai identifies a pair from two annotations: one that marks a colour as active, and one that names the app the pair belongs to. The keys are configurable per tenant. For Expedia they map to the PD controller’s own annotations:

SettingSedai defaultExpedia value
Active colourconfigs.sedai.io/deployment.activeprogressivedeployment.expediagroup.com/active-primary
App nameconfigs.sedai.io/deployment.blue-green-namelabel.spec.app

How a pair is identified

  1. The active annotation must be exactly "true" or "false", and the app-name annotation must be non-blank. Otherwise the workload is treated as an ordinary Deployment.
  2. Sedai derives a logical ID by inserting logical/ into the workload’s ID (logical/stale/ when inactive) and replacing the last segment with the app name. For example, …/myapp-blue with active=true becomes …/logical/…/myapp.
  3. The first workload to claim a logical ID is mapped to it, together with its pods, HPA, VPA and load balancers.
  4. If a second workload produces the same ID, both colours share a value, so a cutover is in progress and the ID is flagged in-progress.
    • Both true (active-active): the second workload is mapped to the /logical/stale/ ID, which is also flagged.
    • Both false: the ID is flagged, and the second workload keeps its physical ID.

What changes in the topology

ResourceChange
DeploymentRenamed to the app name and given the logical ID. Its original ID and name are kept, it is marked as deployment-in-progress when applicable, and release detection is re-run.
PodLinked to the logical app.
HPA / VPATarget rewritten to the logical app.

Release detection runs on the logical ID, so a blue-to-green flip shows up as a release of one continuous app. Settings, metrics history and recommendations carry over.

Pausing actions during a cutover

Before each cycle, every automated action (optimization, availability and the rest) filters out any logical app that is flagged in-progress. The pause lasts only for the overlap window, when both colours carry the same value. Steady state, with one true and one false, is not paused.

Cleaning up after a cutover

When a logical app is no longer discovered but its original physical workload still exists:

  • Active logical app: kept, so its history and settings survive.
  • Stale logical app (/logical/stale/): deleted along with its child resources.
  • The physical workload’s own record: deleted in both cases.

03Annotation-driven settings

On each refresh, every settings.sedai.io/<settingName> annotation on a Kubernetes workload becomes a resource-level setting override. This is general Sedai behaviour, not specific to Expedia. Non-Kubernetes resources use tags with the settings.sedai.io.<settingName> prefix instead.

AnnotationEffect
settings.sedai.io/optimization.setting.configModeOverrides the optimization mode, e.g. DATA_PILOT
settings.sedai.io/availability.configModeOverrides the availability mode
settings.sedai.io/setting.ignoreResourceSetting: "true"Clears all resource overrides back to the inherited group settings, and ignores every other settings.sedai.io/* annotation on the resource

04Recommended configuration

While PD is live, set these two annotations on both the blue and the green Deployment, and do not set ignoreResourceSetting:

settings.sedai.io/optimization.setting.configMode: "DATA_PILOT"
settings.sedai.io/availability.configMode: "DATA_PILOT"

Things to watch for

  1. Don’t combine ignoreResourceSetting=true with configMode=DATA_PILOT. With ignore set to true, Sedai discards the DATA_PILOT annotation and falls back to the group’s mode.
  2. The key name is exact and case-sensitive: settings.sedai.io/setting.ignoreResourceSetting. Variants such as optimization.setting.ignoreresourcesetting are not recognised.
  3. autonomous-optimization.expediagroup.com/enabled is not read by Sedai. It is purely Expedia-side and has no effect on Sedai’s behaviour.
  4. Annotate both colours. Settings are read from each physical Deployment, and either colour can become the logical app after a flip.
  5. The built-in pause is narrow. It only covers Deployments during the overlap window. The annotations above cover the rest of the PD period.

05Scope and reference

Scope and limitationswhat this behaviour does not cover
  • Only Deployments are merged. Argo Rollouts and StatefulSets are checked for the blue/green annotations but are not given a logical ID.
  • Kubernetes Services are not relinked to the logical app.
  • The automatic pause covers the overlap window only. Outside it, Sedai acts on the logical app according to its settings, which is why the DATA_PILOT annotations are recommended for the whole PD period.
